## Implementation audit and feasibility review

- **Scope:** as documented in `UserGuide.md`, enable `explain_before_edit` for supported `edit`, `write`, and `apply_patch` proposals. This is not a sandbox for arbitrary shell/plugin writes. Each proposal, not each line, receives a decision. Disabling the feature retains legacy allow/ask/deny behavior.
- **R1:** `edit.ts` constructs before/after text and signed diff before calling `ctx.ask`. `Permission.ask` validates/trims explanations (1–4000 UTF-16 code units) and marks protected reviews. `getEditReview`/`getEditDiffs` feed `EditExplanation` and `EditBody`; long content is inspectable by scrolling, not necessarily visible all at once. Feasible/checkable; no conflict with R6. Properties check backend-to-presentation data, rendered filename/explanation and multi-file representation, not every pixel or live-model explanation quality.
- **R2:** both existing-file and creation paths await permission before `writeWithDirs`; rejection fails the waiting execution. Configuration deny remains authoritative. The property uses real temporary files, actual edit execution and actual permission replies despite an ordinary allow ruleset. Formatter/LSP are disabled to keep the byte oracle exact. This proves ordering for these paths, not concurrent external writers or every tool.
- **R3:** the actual feedback form's Escape binding invokes `onCancel`, which changes only the local stage back to permission. Enter invokes `onConfirm`, the only feedback reply path. Real rendering, textarea input and SDK request capture make the cancellation observable without duplicating a state machine. No backend cancellation is sent on form cancellation.
- **R4:** feasible but not established: `onConfirm` sends an asynchronous rejection; the server removes pending state and emits a reply. `permission.tsx` does not itself add an explicit completed-with-feedback confirmation. Do not equate a captured HTTP request or a disappeared form with the full visible-status acceptance criterion. This PR does not redesign completion messaging.
- **R5:** `Prompt` derives action order from the same `editReviewOptions` for every language. Left/right (h/l), Enter and Escape use the same selector. Properties compare real character-frame positions at 120 columns and exercise arrow/Enter Accept, Reject and feedback semantics; R3 also checks Escape. This is genuine bounded layout coverage, not proof for all terminal dimensions or user-customized bindings.
- **R6:** feasible; `EditBody` has a shrinking scrollbox, while `Prompt` keeps its action footer outside it with `flexShrink={0}`. Not selected: verifying actual scroll reachability needs a dedicated input/rendering test. No claim that helper output proves scrolling.
- **R7:** `Permission.ask` ignores remembered approvals for protected edits; `reply` downgrades legacy `always` to `once`. A new tool execution obtains a fresh pending ID. R7 checks that even stale A approval cannot release B; a real model is not required or guaranteed to generate B.
- **R8:** `edit`/`write` affect one file; `apply_patch` emits `files` with `filePath`, `relativePath`, `patch`, type, and optional move destination. `getEditReview` deduplicates display labels in first-seen order and names both move endpoints. `getEditDiffs` preserves per-entry patches, including duplicates, or uses the combined fallback for incomplete metadata. The property tests valid multi-file producer semantics, not atomic filesystem application of a patch. Existing helper regressions cover malformed metadata/fallbacks; approval without valid file/diff metadata is not newly claimed safe.

## Properties, generators, isolation, and CI discovery

- Five executable properties cover six requirement IDs and four kinds: invariant, model/oracle, round-trip, metamorphic. Each runs **100 cases**. Seeds: backend **173134**, TUI **173135**. Fast-check reports a seed and shrink path on failure; keep both when reproducing.
- Backend generators vary existing/new files, nested/spaced names, TS/Python/JS/Rust/text extensions, LF/CRLF, 1–8 before/after lines, signed integer content, and explanations including a one-character value and the exact 4000-character boundary. Distinct `old:`/`new:` prefixes ensure a meaningful unambiguous replacement. Each case rejects once and approves a subsequent proposal, so both outcomes are exercised rather than left to random choice.
- Feedback generators include empty/whitespace, multiline, accented and Arabic text, arbitrary bounded strings, and 1–3 repeated cancellation cycles. R7 also checks the blank-feedback plain-rejection semantics.
- UI generators use readable, bounded proposal data so layout comparisons do not confuse terminal escapes with code. R5 compares two proposals at one fixed viewport; R8 generates 2–8 unique paths then deliberately reorders/duplicates them and includes moves.
- Actual feature logic is not mocked. Backend fixtures isolate only account/auth/package/network access. UI fixtures intercept HTTP while retaining the real dialog, keymap, SDK serialization, and renderer. Temporary directories are scoped/disposed; edit fibers are scoped per case and renderers destroyed in `finally`. No model/provider requests or real user-file mutations are needed.
- Reuse fast-check **4.8.0** already added to `packages/opencode` by merged dependency PR #32. Declare the same existing version as a TUI development dependency for tests living there; lockfile change is only that workspace declaration, not a second version or dependency graph update.
- `turbo.json` already includes `opencode#test` and `@opencode-ai/tui#test`; no Turbo or workflow change is needed. The PR `test` workflow runs both full suites. Each property emits a concise success record **only after** its assertion completes, identifying its file, requirements, case count and seed despite full-suite `--only-failures`. Failures still fail the normal package task. The available OAuth token cannot modify workflows, so redundant focused workflow steps were removed before pushing; existing CI coverage is unchanged.
